# 智能问数行业收敛方向（2026）

> 编译自 [[智能问数Agent全网深度调研-2026-08-03]] §0（L10–56）、§1（L59–86）。

## 核心问题
2026 年智能问数 / Data Agent 领域，领先开源项目与商业系统的共同架构方向是什么？Data-Agent 应该对齐什么、拒绝什么？

## 关键结论

**范式转移**：领先项目已从「NL → SQL」转向「**上下文构建 → 受治理语义计划 → 确定性执行 → 结果验证 → 反馈回灌**」（§0.2，L31）。

**五个共同收敛机制**（§0.2，L33–39）：
1. **语义对象先于 SQL**：指标、维度、关系、粒度、过滤、时间含义先结构化，再生成/执行查询。
2. **组织知识进入版本化资产**：术语、规则、verified queries、历史成功查询、数据质量与来源不再只塞 prompt。
3. **Agent 不直接拥有事实解释权**：Agent 负责理解、规划、叙事；指标计算、关系展开、权限、快照、证据由确定性系统负责。
4. **用户反馈必须经审核再沉淀**：Snowflake VQR、Genie knowledge mining、Wren memory、ktx reconciliation 都在做这层。
5. **评测从 SQL 字符串比较升级为执行结果与回归**：跑 SQL、比结果、测 regression 和 latency。

**路线判断**（§0.1，L12–27）：最适合 Data-Agent 的不是整体迁入 WrenAI / DB-GPT / Datus / 多 Agent 框架，而是：
- 保留汽车测试领域数据能力；
- 建 **Wren/Cube/MetricFlow 风格的确定性 Semantic Kernel**；
- 加 **ktx/OpenMetadata 风格的可审查上下文建设面**；
- 加 **Snowflake/Genie 风格的 verified-query/eval 飞轮**；
- 在线主链路保持「一个主 Agent → 有界 model→tool→observation 循环 → 少量类型化分析原语 → 隐藏的确定性 Semantic Kernel → 固定快照数据执行 → Claim→Evidence 校验后回答」。

**明确反对**：把 CHESS/CHASE-SQL 的四 Agent、多候选投票放进在线主链路——benchmark 有效但时延/成本/不可观测分支代价高，只适合离线评测或按阈值触发的兜底（§0.1，L27）。

## 操作要点
