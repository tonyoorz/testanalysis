# PreAnalysis 完整数据流梳理

## 数据源

- **Octane**（企业级测试管理与缺陷管理系统），是本项目所有分析数据的唯一源头系统，涵盖以下业务对象：
  - Defect（缺陷主表）
  - Manual Run（人工测试执行记录）
  - Defect History（缺陷状态变更历史）
  - Project / Team 等维度信息（供 Ontology 关联使用）

## 下载链路

项目中存在**两套下载器**，功能定位不同：

| 下载器 | 路径 | 特点 |
|---|---|---|
| 主下载器 | `download/octane_downloader.py` | 默认**直写数据库**（除非加 `--skip-db` 参数） |
| 历史下载器 | `downloader7.py` | 纯**文件落地流程**，无数据库写入逻辑，落地到 `history/*.json` |

字段定义对齐（两者一致）：
- `DEFAULT_F_DEFECT_MAIN`：**40 个字段**
- `DEFAULT_F_MANUALRUN`：**30 个字段**

已知抓取参数差异（潜在风险点）：
- History 抓取单票 limit：`downloader7.py` 为 **10000**，`octane_downloader.py` 为 **5000**，极端情况下可能造成历史记录截断不一致。

## 处理与清洗

- 数据落地后分两条并行路径流转：
  1. **数据库路径**：`octane_downloader.py` 写入后进入 SQLite（后续可双写 PostgreSQL）。
  2. **本地文件路径**：`downloader7.py` 产出的 `history/*.json` 等文件，仍被部分分析模块直接读取，尚**未完全退居为备份角色**，例如：
     - `data_processor.py:3298`
     - `data_processor.py:3810`
     - `longrunner_analysis.py:93`
     - `longrunner_analysis.py:289`
- 读取策略：**DB优先 + 文件回退（db_first）**
  - 配置位置：`db_migration_config.py:14`（读取模式 `db_first`）、`db_migration_config.py:20`（写入模式默认 `both`）
  - `defect_explore6.py:669` 主加载入口设置 `use_db=True`，但底层 `data_processor.py` 的 `load_defect_data` / `load_test_data` 仍保留文件级回退逻辑。
- 特征加工层：由 `data_processor.py` 统一承担字段解析、JSON 反序列化、指标聚合、长跑（long-runner）分析等，是清洗与特征生成的核心枢纽。

- 项目已具备 PostgreSQL 支撑代码，**非从零搭建**：
  - `requirements.txt:55`（依赖 `psycopg`）
  - `deploy/start_postgres.sh:1`（本地 PG 容器启动脚本）
  - `init_postgres_db.py:1`（PG 表结构初始化脚本）
- 当前状态：**字段兼容、结构已就位，但数据尚未真正迁移导入**，PG 侧三张核心表均为 0 条记录。
- 真正支持从 PG 读取数据的模块是 `UnifiedDataLoader`（`unified_data_loader.py:526`、`unified_data_loader.py:773`），已完成 smoke test，SQL 查询可跑通（因 PG 为空，当前返回 0 行）。
- 技术选型结论：主库升级方向为 **PostgreSQL 16 + pgvector**（结构化查询 + 语义检索统一底座），DuckDB 仅作为可选的二阶段分析加速层，不替代主库。迁移原则为**先双写不切读**，确保任意阶段可回滚，不破坏现有 SQLite 与本地文件逻辑。

## 已知断点与风险

1. **数据未真正迁移**：PG 表结构已就位、字段兼容，但三张核心表（defects/manual_runs/histories）实际数据量均为 0，展示层尚未从 PG 读取，"双写"目前仅停留在代码能力层面，未在生产数据流中生效。
2. **本地文件依赖未清除**：`downloader7.py` 产出的 `history/*.json` 仍被 `data_processor.py`、`longrunner_analysis.py` 等多处直接读取，并非纯粹的备份/回退角色，与"DB优先"的既定策略存在实际执行落差。
3. **两套下载器并存造成口径风险**：`octane_downloader.py`（写库）与 `downloader7.py`（纯文件）的 History 抓取 limit 参数不一致（5000 vs 10000），极端场景下可能导致两条链路的历史数据完整性不一致。
4. **约束差异导致的潜在迁移失败风险**：SQLite 中允许为空的字段（如 `defect_id`/`raw_json`/`fetched_at`/`mr_id`）在 PG 中为 NOT NULL，若历史数据存在空值，直接迁移会触发约束冲突，需先做数据清洗或默认值填充。
5. **展示层版本分叉**：`defect_explore6.py` 与 `defect_explore_modern.py` 并存，样式改造目前仅限定在 `defect_explore_modern.py` 单文件内，未来若两版本数据口径或加载逻辑出现差异，可能造成展示不一致。
