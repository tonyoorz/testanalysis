# 工程治理与环境维护

> 项目仓库管理、磁盘清理、技能/PPT 制作等工程治理事项。综合 10 篇知识页。

## 主题概述

本主题聚合了项目在日常工程实践中围绕**代码仓库治理、开发环境配置、系统资源维护、存储架构演进与工具链管理**所积累的经验与踩坑记录。涵盖 Git 分支同步策略、AI 编程工具（OpenClaw/Codex/Claude Code）的安装配置排错、Mac 系统磁盘清理、SQLite→PostgreSQL 迁移评估、技能/插件生态选型，以及远程协作基础设施搭建，是保障多项目并行开发不"翻车"的底层保障工作。

## 核心知识

### Git 分支管理与仓库同步

分支管理暴露出两个典型风险模式：

- **分支滞后与分叉风险**：Data-Agent 仓库本地分支 `feature/2026-06-22-p1-complete` 与远端同步（0 ahead/0 behind），但**并非仓库最新分支**——远端已有 `feature/2026-06-29-auth-system`、`feature/2026-07-01-data-agent-sync`（最新）。切换到最新分支后发现其近期提交（dashboard analytics、qgate refresh、voice transcribe）与本地正在做的 P1 系列安全加固工作差异很大，**提示分支可能已分叉**，本地改动（AST 安全加固）不一定存在于新分支，需要人工核对合并策略。
- **多人协作下的被动追赶**：`vizion-lab` 项目远程仓库由其他协作团队持续推进（先后出现 37→58 个提交的领先差距），团队用 **DuckDB WASM**（`src/lib/duckdb/`）和 **Pyodide**（`src/lib/pyodide/client.ts`）替换了本地新建的纯前端 `fileParser.ts` 方案。标准同步流程为：`git fetch` 比对差异 → `git pull`（fast-forward）→ 拉取后重新 `npm install` 补齐新依赖 → 本地改进独立建分支（如 `codex/ui-upgrade-20260529`）push 后走 PR 流程，而非直接合并到主线。

**共性教训**：分支"与远端同步"不代表"是最新版本"，多分支/多协作者场景下必须显式比对 `git branch -a` 全量分支列表，且拉代码后要检查依赖变更。

### 开发工具/AI 助手环境配置排错

多个知识页记录了 AI 编程工具的环境搭建痛点，核心矛盾都是**"多套体系/多套凭证容易混用"**：

- **OpenClaw 启动报错链**：表面报错 `No API key found for provider "anthropic"` 与实际网关健康、设备配对失败（`code=1008 reason=pairing required`/`device signature expired`）是两个独立问题，容易误判。
  - **Moonshot（OpenAI 兼容）**：`MOONSHOT_API_KEY`，模型 `moonshot/kimi-k2-turbo-preview`，baseUrl `https://api.moonshot.cn/v1`
  - **Kimi Coding（Anthropic 兼容）**：`KIMI_API_KEY`，模型 `kimi-coding/k2p5`，baseUrl `https://api.kimi.com/coding/`
  - 用户曾将 Kimi Code 的 key（`sk-kimi-...`）误用作 `MOONSHOT_API_KEY`，导致持续 `HTTP 401`；最终排查方式是脱离 OpenClaw 配置层，直接用 `curl` 打官方接口验证 key 有效性——**绕开中间层直接验证凭证是定位 401 问题的关键手段**。
  - 结论：**skill 不能解决模型知识过时问题**，skill 只提供流程/工具能力，获取最新信息核心依赖联网检索（web search）。
- **Codex Windows 桌面版安装**：官方推荐渠道为 Microsoft Store（`winget install Codex -s msstore`），系统要求 Windows 10 19041.0+。原生运行于 PowerShell + Windows sandbox，也可配置到 WSL2（使用 `bubblewrap` Linux sandbox，0.115 起不再支持 WSL1）。**关键坑点**：Windows 应用与 WSL 内 CLI 默认不共享配置/凭证/会话历史（各自独立 `.codex` 目录），需手动设置 `CODEX_HOME=/mnt/c/Users/<windows-user>/.codex` 才能打通。
- **Claude Code 远程访问方案选型**：因 Claude 官方 App 国内不可用，最终选定开源方案 **Happy**（`slopus/happy`），用 `happy claude` 包装原生 `claude` 命令启动，手机端接管时会话自动切远程模式。对比方案包括官方 Remote Control（`/rc` 命令，`/config` 开启自动远控，但存在 GitHub Issue #30691 手机 App 不显示会话的已知问题）、SSH 直连（Termius/Termux）、tmate/ttyd 中继（需自建避免第三方依赖）。环境记录：Node v22.22.3、npm 10.9.8、Claude Code 2.1.63，本地用 `cc-switch` 工具切换多套 API 配置（GLM/智谱接入）。

### 系统资源与磁盘空间维护

两轮 Mac 磁盘清理记录了系统性的空间治理方法论：

- **累计释放约 54GB**，明细：
  - Ollama 模型清理：`llama3:8b`(4.7GB) + `qwen3:0.6b`(522MB) = 5.2GB（保留仍活跃的 `qwen3-embedding:latest` 4.7GB）
  - Downloads 冗余压缩包/DMG：约 1.07GB（`PYQT 2.zip`、`QClaw-*.dmg`、`dify-for-dsl-*.zip` 等）
  - JetBrains 缓存 + Steam App Support：3.3GB
  - npm 缓存 + 开发残留（Codeium、Chromium 旧快照、EasyOCR 模型、.venv）：约 5.0GB
  - 大型软件卸载：`Windows 10.pvm`（38GB，长期未用）、ClashX（47MB）
- **待决策的大项目目录**（尚未清理，需用户确认）：`~/aianalysis/`（30GB）、`~/LLaMA-Factory` 等
- **安全隐患发现**：`~/Downloads` 目录直接存放敏感凭证文件（`AccessKey.txt`、`s3access_credentials.csv`、`tonyorz.pem` 等），建议迁移至密码管理器而非清理删除。
- 诊断方法：桌面/下载目录文件数量与重复度统计（Downloads 达 210 个文件，含大量 `(1).png` 重复及 Office 临时文件）是判断"混乱度"的直接信号。

### 数据存储架构演进（SQLite → PostgreSQL）

- **字段兼容性核查**：`octane_payloads`、`octane_defect_histories`、`octane_defects`、`octane_manual_runs` 四张表字段名/数量在 SQLite 与 PG 间一一对应，可迁移；但 **PG 约束更严格**——`octane_defects.defect_id/raw_json/fetched_at`、`octane_manual_runs.mr_id/raw_json/fetched_at` 在 PG 为 NOT NULL（SQLite 当前允许空），`octane_payloads.year` 在 PG 为 NOT NULL 默认 -1。
- **读取链路现状**：`defect_explore`/`data_processor` 目前仍走 SQLite（`data_processor.py:921`），真正支持 PG 读取的是已做过 smoke test 的 `UnifiedDataLoader`（`unified_data_loader.py:526`, `:773`）。
- **迁移进度（数据量对比，字段兼容但数据未导入）**：
  - defects: SQLite 15298 条 vs PG 0 条
  - manual_runs: SQLite 34333 条 vs PG 0 条
  - histories: SQLite 8493 条 vs PG 0 条
- 项目已具备迁移基础设施（非从零搭建）：`requirements.txt:55`（`psycopg`）、`deploy/start_postgres.sh:1`、`init_postgres_db.py:1`。

### 工具链与技能生态治理

- **技能选型方法论**：使用 `skill-installer` 对比官方精选库与 GitHub 高热度技能，以 Star 数与功能完整度（是否覆盖生成/渲染/QA 全流程）作为决策依据，例如为制作 PPT 选定 `anthropics/skills` 仓库下 `pptx` 技能（约 16.1 万 Star），安装于 `/Users/tonyorz/.codex/skills/pptx/SKILL.md`。
- **批量技能安装实践**：OpenClaw 侧已批量安装 OpenAI curated 全量 30 个热门 skill（`playwright`、`pdf`、`screenshot`、`spreadsheet`、`speech`、`transcribe`、`security-*`、`vercel-deploy` 等）。
- **第三方插件依赖风险**：OpenClaw 自带的 `feishu` 插件（社区维护版）存在依赖缺失问题，需转向社区包 `@m1heng-clawd/feishu`（落地目录 `/Users/tonyorz/.openclaw/extensions/feishu`）。

### Agent 平台自建 vs 借力的治理判断

在"是否需要重造类似 openclaw 的平台"的讨论中形成明确结论：**没必要**。项目已具备"分析型 Agent"完整骨架（工具链、上下文构造、记忆、解释、质疑模块齐备），与业务数据强耦合并已有 PostgreSQL 迁移双写通道，不存在被 SQLite 锁死的风险。真正差距在于**工程治理**（核心文件过大）、**评测闭环未形成门禁**、**可观测性缺统一指标**、**文档与仓库现状存在偏差**——最优策略是借鉴通用平台的能力（评测、追踪、治理）压缩为项目场景下的最小可用模块，而非重建平台。
