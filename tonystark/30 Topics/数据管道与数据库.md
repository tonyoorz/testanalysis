## 主题概述

本主题围绕项目数据链路的核心议题——**SQLite 向 PostgreSQL(+pgvector) 的迁移评估与落地**——展开，涵盖字段/约束兼容性核对、Octane 下载器到数据库的写入现状、看板(defect_explore 系列)的数据读取路径，以及最终的数据库选型决策。另收录两篇与本主题内容关联度较低的知识页（Codex 桌面版下载、Claude Code 手机远程监控），仅作背景记录，未纳入核心综合。

## 核心知识

### SQLite → PostgreSQL 字段与约束差异
- 四张核心表 `octane_payloads`、`octane_defect_histories`、`octane_defects`、`octane_manual_runs` 在 SQLite 与 PostgreSQL 间字段名、列数量一一对应，**基本可迁移**。
- PG 侧约束更严格：
  - `octane_defects`：`defect_id`/`raw_json`/`fetched_at` 为 NOT NULL（SQLite 当前可为空）
  - `octane_manual_runs`：`mr_id`/`raw_json`/`fetched_at` 为 NOT NULL（SQLite 当前可为空）
  - `octane_payloads.year` 为 NOT NULL，默认值 `-1`
- 项目已有 PG 支持代码基础（非从零搭建）：`requirements.txt:55`（`psycopg`）、`deploy/start_postgres.sh:1`（本地 PG 容器）、`init_postgres_db.py:1`（初始化表）。

### 数据下载与写入链路现状
- 存在两套下载器：
  - `download/octane_downloader.py`：默认写数据库（除非加 `--skip-db`）
  - `downloader7.py`：纯文件落地流程，无数据库写入逻辑
- 字段定义一致：`DEFAULT_F_DEFECT_MAIN`、`DEFAULT_F_MANUALRUN` 均为 40/30 字段，覆盖对齐。
- **History 抓取存在潜在截断风险**：`downloader7.py` 单票 history limit=10000，`octane_downloader.py` 为 5000，极端情况下可能截断数据，两者未统一。
- 当前 DB 实际数据量与本地文件数量一致（对齐状态）：`octane_defects=15298`、`octane_manual_runs=34333`、`octane_defect_histories=8493`。
